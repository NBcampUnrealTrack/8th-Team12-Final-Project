# 미니게임 구현 방식 정리

햄버거집 알바 미니게임(기획 HTML 시안 `play.html`)을 언리얼로 옮기면서 검토한 방식들과,
지금 채택한 구조를 정리한다. 꽃 · 서바이버 미니게임도 같은 틀을 쓴다.

---

## 1. 지금 구조 (채택)

### 1-1. 흐름

```
[테스트 맵 L_MiniGameTest]
  AMiniGameDoor  ── E키 상호작용 ──▶  OpenLevel(L_BurgerHouse)

[L_BurgerHouse]  (팀원 맵 · 수정 없음)
  UMiniGameSubsystem::OnWorldBeginPlay
    ├─ MiniGame Setting에서 "L_BurgerHouse" 항목을 찾는다
    ├─ 플레이어를 카운터 뒤 주방으로 이동 (손님 동선과 분리)
    ├─ 캐릭터 이동 · 시점 입력 잠금, 입력 모드 UI 전용
    └─ UBurgerMiniGameWidget 생성 → AddToViewport(50)

  위젯: 60초 플레이 → FinishGame() → 보상 지급 (돈 40,000 + 손재주 1~5, 한 번만)
        "퇴근하기" → ExitGame()

  UMiniGameSubsystem::EndMiniGame
    ├─ 위젯 제거, 입력 원복
    └─ UMiniGameTravelSubsystem: 들어오기 전 레벨로 OpenLevel
```

### 1-2. 구성 요소

| 파일 (`Source/Febricula/.../MiniGame/`) | 역할 |
|---|---|
| `MiniGameSettings` | Project Settings > MiniGame Setting. **레벨 이름 → 미니게임 위젯 · 시작 위치 · 보상** 표 |
| `MiniGameSubsystem` | 레벨 시작 시 미니게임 띄우기, 보상 지급, 종료 후 복귀 (World 서브시스템) |
| `MiniGameTravelSubsystem` | 이전 레벨 기억 (GameInstance 서브시스템 - 레벨을 넘어가도 유지) |
| `MiniGameWidget` | 위젯 베이스. `FinishGame` / `PreviewReward` / `ExitGame` |
| `MiniGameDoor` | E키로 지정 레벨 이동. 기존 `InteractionComponent`가 그대로 감지 |
| `Burger/BurgerMiniGameWidget` | 햄버거 게임 규칙 + 화면 (`NativePaint`) |

### 1-3. 화면을 그리는 방식 — 위젯 트리 없는 C++ 위젯

```
화면(Viewport)
 ├─ PlayerHUDWidget         기존 HUD (손대지 않음)
 └─ BurgerMiniGameWidget    Z-order 50
     └─ 840×1240 가상 캔버스를 화면 높이에 맞춰 가운데 배치
        양옆은 투명 → 3D 햄버거집(손님 NPC)이 배경으로 보인다
```

- WBP 디자이너에 이미지·텍스트를 배치하지 않는다. `NativePaint`에서 배경 · 주문판 · 재료 · 캐릭터를
  **HTML 캔버스와 같은 좌표·크기 숫자**로 직접 그린다 (`FSlateDrawElement::MakeBox / MakeText`).
- 키보드는 위젯이 직접 받는다 (`NativeOnKeyDown`). 버튼은 그림 + 마우스 영역 판정.
- 텍스처 26장: `/Game/MiniGame/Burger/Textures/` (최근접 필터 · 밉맵 없음 · UI 압축).

### 1-4. 이 구조를 고른 이유

| 이유 | 설명 |
|---|---|
| 남의 맵을 안 건드린다 | 시작 위치 · 미니게임 종류를 **설정(ini)** 에 둬서 `L_BurgerHouse` 맵 파일을 저장할 일이 없다 |
| HTML 시안을 숫자 그대로 옮긴다 | 좌표계가 같아서 기획이 시안을 고치면 숫자만 옮기면 된다 |
| 3개 게임이 틀을 공유 | 시작 · 정산 · 복귀는 공통. 게임마다 위젯 클래스 하나만 새로 만든다 |
| 에디터 연결 없이 개발 가능 | WBP 작업이 없어 코드만으로 빌드 · 수정 · 디버그 |
| 손님 NPC와 충돌 없음 | 플레이어를 주방(내비메시 밖)에 세워 손님 동선을 막지 않는다 |

## 2. 검토한 방식 비교

### 2-1. 어디에 띄우나

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 기존 HUD 안에 넣기** | `PlayerHUDWidget`(WBP)의 Overlay에 미니게임 패널을 추가하고 보이기/숨기기 | 위젯이 하나라 Z-order 관리가 쉽다 (HUD 설계 의도와 같음). 대화창과 같은 스타일 공유 | **HUD WBP가 공용 파일** — 대화 · 프롬프트 담당과 충돌. HUD가 미니게임 3개 내용을 다 품어 비대해진다. 미니게임 없는 레벨에도 항상 로드 |
| **B. 별도 위젯을 Viewport에 추가** (채택) | 미니게임 위젯을 따로 만들어 HUD 위(Z 50)에 띄우고, 끝나면 제거 | HUD와 완전히 분리 — 서로 수정이 안 부딪힌다. 필요할 때만 생성. 게임별 교체가 쉽다 | Z-order를 신경 써야 한다 (HUD 프롬프트가 위로 올라오지 않게). 입력 모드 전환을 직접 관리 |
| C. AHUD 캔버스 (`DrawHUD`) | 게임모드의 HUD 액터에서 `Canvas->DrawTexture`로 그리기 | UMG 없이 가장 단순한 즉시 그리기 | **게임모드 HUD 클래스를 바꿔야 한다** (공용). 클릭 · 포커스 · 해상도 대응을 전부 직접. UE4식 구식 방법 |
| D. 월드에 배치 (Paper2D / 액터) | 레벨 안에 스프라이트 · 카메라를 놓고 2D 게임처럼 | 조명 · 파티클 등 3D 연출 가능 | **맵 파일을 수정**해야 함. 카메라 전환 · 충돌 · 해상도 대응이 무겁다. 2D UI 게임에 과함 |
| E. 미니게임 전용 레벨 | 빈 레벨에서 미니게임만 실행 | 다른 시스템과 완전 격리 | 햄버거집 배경(손님 NPC)을 못 쓴다. 레벨이 3개 더 늘어난다 |

**HUD에서 띄우는 것(A)도 가능하다.** HUD가 이미 "한 위젯 안의 Overlay로 쌓는다"는 설계라
패널 하나를 더 얹으면 된다. 다만 HUD는 대화 시스템 담당 파일이고, 미니게임 3개를 다 넣으면
충돌과 비대화가 커서 B를 골랐다. B도 HUD 위에 겹쳐 뜨므로 화면상 결과는 같다.

### 2-2. 화면을 어떻게 그리나

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **① C++ `NativePaint` 직접 그리기** (채택) | 위젯 트리 없이 C++에서 좌표로 그린다 | HTML 캔버스 코드와 1:1 대응 — 이식이 빠르다. 떨어지는 재료 수십 개처럼 **수가 변하는 오브젝트에 유리** (위젯 생성/삭제 없음). 에디터 없이 개발 | 디자이너가 화면에서 끌어다 고칠 수 없다 (숫자 수정). 레이아웃 변경마다 컴파일 |
| ② WBP 디자이너 + C++ 로직 | `BindWidget`으로 Image/TextBlock을 연결, 로직만 C++ | 디자이너가 직접 배치 · 폰트 · 애니메이션 편집. UMG 기능(애니메이션, 스타일) 그대로 사용 | 떨어지는 재료처럼 **동적 오브젝트는 위젯을 매번 생성/풀링**해야 한다. WBP는 바이너리라 git 충돌 시 병합 불가. MCP/에디터 작업 필요 |
| ③ 혼합: ① 상속 WBP | ①의 C++ 위젯을 부모로 WBP를 만들고 장식만 WBP에 얹기 | 게임 화면은 코드, 프레임 · 타이틀 연출은 디자이너가 | 두 곳을 봐야 한다 |
| ④ Web Browser 위젯 | HTML을 그대로 띄우기 | 이식 작업 0 | **WebBrowser 플러그인(CEF) 필요**, 패키지 용량 · 시작 시간 증가. 입력 포커스 · 보상 연동(JS↔C++)이 불안정. 콘솔 미지원 |

**지금은 ①로 만들고, 아트 연출이 필요해지면 ③으로 확장**할 수 있다
(예: 타이틀 화면만 WBP 애니메이션).

| 항목 | 값 | 위치 |
|---|---|---|
| 돈 | 40,000 고정 (기획 확정) | `GameProgressSubsystem` 카운터 `Money` (아직 돈 시스템이 없어 카운터 사용) |
| 손재주 | 기본 1 + 완성 주문 수가 {3, 5, 7, 9}를 넘을 때마다 +1 → 1~5 | `GameProgressSubsystem` 스탯 `HandWork` |

| 항목 | 값 |
|---|---|
| 규칙 | 90초. 같은 꽃 둘이 닿으면 다음 단계(씨앗→…→꽃다발). 주문 꽃이 피면 자동 포장. 위험선 위 2초면 종료 |

| 튜토리얼 | 첫 판은 연습 판 5단계(놓기 → 합치기 → 데이지 → 튤립 주문 → 위험선), 이후 설명 카드 3장 · 대충 일하고 퇴근 |
| 시작 | `FlowerHouse` 레벨이 열리면 자동 시작. 테스트 맵 `L_MiniGameTest`의 햄버거 문 옆 꽃집 문으로 이동 |
| 에셋 | `/Game/MiniGame/Flower/Textures/` 14장, `/Game/MiniGame/Flower/Audio/SFX/` 7개 (BGM 없음) |

## 4. 새 미니게임 추가 방법 (꽃 · 서바이버)

1. `UMiniGameWidget`을 상속한 위젯 클래스를 만든다 (규칙 + `NativePaint`).
2. 끝날 때 `FinishGame({Score})`, 결과 확인 버튼에서 `ExitGame()`.
3. MiniGame Setting > Levels에 `레벨 이름 → 위젯 클래스 · 시작 위치 · 보상` 한 줄 추가.
4. 출발 맵에 `MiniGameDoor`를 놓고 `TargetLevel` 지정.

시작 · 입력 전환 · 보상 지급 · 복귀는 공통 코드가 처리한다.
